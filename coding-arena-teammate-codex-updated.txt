CODING ARENA — PROJECT CONTEXT AND FROZEN PLAN

This replaces the Decision Receipt / Airlock / Mission Control implementation plans. Build Coding Arena only. Use the new repository:
https://github.com/kumar-varun024/CodingArena

Goal: a human-led Switch workflow in which two coding agents independently solve the SAME repository task, present frozen submissions, challenge each other with executable evidence, repair their own code, and return a tested patch for a human to select. A tie or no acceptable result is valid. Passing tests means passing the recorded checks, not proof that code is bug-free.

The two Codex development chats build this product. They are NOT automatically the two runtime contestants. The runtime contestants are separately registered Switch agents. Two Codex agents are sufficient; different providers are optional. Display actual provider/model settings when known and never invent a model identity or claim a universal model ranking from one match.

MVP SCOPE
- Local-first. One active match, two agents, one Python task pack, one challenge phase, at most two repair rounds.
- Task pack booking-v1: implement src/booking.py with BookingSystem, booking/cancellation/capacity/group atomicity requirements defined in the interface manifest.
- This is a real code module and executable tests, not a full booking website. Arbitrary repositories/tasks, payments, concurrency stress testing, hosted SaaS, tournaments, automatic GitHub merging and model-based scoring are later scope.
- Both contenders start from the same sanitized task Git base and frozen specification. Each has a separate disposable checkout. Public tests are available; held-out tests and the reference implementation stay in the runner.
- Agents submit their OWN commits, never edit their rival's frozen snapshot. Challenger scenarios are bounded JSON operation sequences interpreted by a trusted driver, not arbitrary uploaded test programs.
- A report cites requirement IDs and must pass the trusted reference and fail the exact opponent snapshot twice to count as reproduced. A human still decides whether the expectation matches the requirement.
- Accepted scenarios become regression tests for BOTH candidates. Repair does not combine their code. Any future hybrid would be a new candidate needing full verification.
- No mandatory winner. Every accepted regression and all baseline/held-out checks must pass on the latest exact snapshot before it can be selected. Pending decisions, stale evidence, timeouts and runner errors cannot become success.
- Initial comparison plus one repair is the demo target; a second repair is the cap, not an infinite loop. Both broken after the cap -> neither, with specific blockers and evidence.
- Switchboard is optional future development/review support. It is not a dependency of the MVP and does not automatically run agents on the teammate's laptop.

HOW SWITCH IS USED
Use Switch's native coding-agent runtime via Console; do not add another agent framework or build a custom Switch protocol client for this MVP. The arena engine runs tests and stores evidence; it does not call model providers or secretly replace Switch dispatch.

Create three rooms: arena-build-a, arena-build-b and arena-review. Each build room contains only its own contender and the relevant human(s). Put the identical frozen task card in both. Do not put rival approaches, diffs, private tests or code in a common room during the independent build phase. Only after both initial candidates freeze does the operator reveal them and bring both agents into arena-review. The agents remain out of the other agent's build room.

Each native Switch agent uses the B-owned arena_client.py to fetch its assignment, run public practice checks, submit its code, submit challenge scenarios, mark review complete, and poll actual job results. It posts a short evidence-linked presentation in Switch. After a human initiates review/repair, address the appropriate agent in the correct room; use bounded follow-ups and await completion before moving it to another room. Do not assume a message wakes an unaddressed or unauthorized agent.

The human decides semantics in Switch, then records the formal acceptance/rejection or final selection in the local operator dashboard/CLI linked from that conversation. These are explicit operator actions. The MVP does not infer authenticated approval from an agent saying a human approved, and does not pretend there is a verified Switch webhook. Record genuine room/message IDs if available; otherwise store null IDs and truthful unverified/operator-recorded provenance.

Example room messages:
1. In each build room: '@arena-a [or @arena-b] fetch your assignment for MATCH. Implement booking-v1 in your assigned checkout. Run public checks, commit the allowed change, submit and report the returned candidate ID and verification job.'
2. After reveal in arena-review: '@arena-a review candidate B. Find at most two concrete requirement violations. Submit JSON reproductions through the client, poll the jobs, and mark your review complete even if you found none.' Repeat for B.
3. Human: 'The cancellation rule is BOOK-04: a second cancellation must change nothing. I accept the reproduced claim.' Operator records this decision; the engine updates the suite.
4. In each build room after start_repair: 'Repair your own implementation against the accepted findings; submit a new commit, or resubmit unchanged code if it is already correct.'
5. Human asks agents to explain remaining tradeoffs; dashboard shows current measured evidence. Human selects A, B or neither and downloads a patch/evidence pack.

Runtime setup: choose one demo machine for the engine, task checkouts and BOTH native Switch agents. Keep each agent registered to its pre-created stable slot root. The two developers can use separate laptops and push their product code normally. Configure ARENA_API_URL for the actual agent host; localhost on the teammate's laptop is a different machine. Remote filesystem synchronization is not part of the MVP. Use bundled Mattermost or an already-accessible chat bridge. A GitHub collaborator is not automatically a Switch/chat participant. Check agent addressing permissions for the demo participants. Verify the runtime is connected; do not assume keeping only a browser tab open keeps an agent alive.

Separate rooms and checkouts prevent accidental mixing; on one OS account they are not a hostile-agent secrecy guarantee. Generated contestant code executes in the engine's restricted Docker runner. This is a cooperative demonstration on synthetic task data, not an adversarial hosting platform.

SHARED INTERFACE
All backend communication uses /api/v1 JSON over HTTP, defined completely by interface 1.1 in the manifest below (or an identical companion coding-arena-interface-v1.1.json). The dashboard and Switch client must not import engine internals or query its SQLite directly. Every /api/v1 HTTP response carries X-Arena-Mode: fixture or live, including errors and artifact downloads. Only /health and Match additionally define a top-level JSON mode field; do not add that field to other response bodies. The API client captures the header for all responses and treats a missing/invalid header or conflicting body mode as an unknown-mode protocol error. The fixture server always identifies itself as fixture. The live engine identifies itself as live. Proxies preserve this header; cross-origin setups expose it to the configured UI origin. A owns all digests, state transitions, candidate eligibility and truth of test outcomes. B renders them without recalculating winners.

Phases: building -> reviewing -> repairing -> verifying -> decision -> complete. The no-repair path is reviewing -> verifying. A second repair may start at decision, within the cap. Cancellation is explicit. The detailed guards, error recovery and no-winner rules are normative in the manifest.

A proof scenario is executable JSON, for example: capacity 3; book('family',2) returns true; cancel('family') true; cancel('family') false; available() equals 3. A scenario proves state only if it checks state; a false return alone is insufficient. Expected values use strict JSON types. Agents cannot edit the oracle to make their solution pass.

Client retry behavior: the dashboard also saves each non-secret operation ID and request body before sending, reuses them after ambiguous timeouts, and displays the request ID for recovery. Tokens remain in memory. Practice results are labelled separately and never establish candidate eligibility. A stages opponent review copies inside the reviewer's fixed slot root, and Assignment.review_path points there. The early Switch smoke is only a harmless local command until the real engine and tokens are available.


INTERFACE 1.1 CLARIFICATIONS
- Challenge file: challenge --file challenge.json reads a UTF-8 JSON object with exactly title, requirement_ids and scenario. title is a non-empty string; requirement_ids is a non-empty array of unique IDs from the frozen booking requirements; scenario follows Scenario. Reject missing/extra top-level fields and invalid types. A bare Scenario is not the file format. The client adds target_candidate_id from --target, the persisted request_id, and source from its flags; credentials and those metadata fields are not file fields. The API independently validates the request.
  Complete challenge.json example:
  {"title":"Repeated cancellation preserves available capacity and reservations","requirement_ids":["BOOK-03","BOOK-04"],"scenario":{"capacity":3,"steps":[{"op":"book","args":["family",2],"expected":true},{"op":"cancel","args":["family"],"expected":true},{"op":"cancel","args":["family"],"expected":false},{"op":"available","args":[],"expected":3},{"op":"reservations","args":[],"expected":{}}]}}
- Provider labels: POST /matches requires provider_labels with exactly a and b, each a non-empty display string or null when unknown. A persists these values unchanged and returns them in Match and Assignment, including after restart and before reveal. B renders null as Unknown and supplied labels as operator-recorded configuration, not verified provider identity. Do not invent missing model settings or rank models from one match.
- BOOK-07 coverage: JSON challenge scenarios use one instance, so they cannot prove isolation between BookingSystem instances. A must include a trusted baseline and/or held-out check in every full official verification that creates at least two objects in one process and checks that booking/cancellation on either leaves the other's capacity and reservation mapping unchanged. The single-instance challenge DSL stays unchanged; agents must describe this coverage limit honestly.
- Fixture identification: X-Arena-Mode is required on every /api/v1 response, including auth/validation errors, short mutation responses and text/JSON artifacts. Use fixture for all fixture-server responses and live for live-engine responses. Retain top-level mode only where already defined (/health and Match); keep other JSON and text bodies unchanged. B's shared client exposes the header on success, error and download paths. A missing/invalid header or conflicting body mode is a protocol error with unknown mode, never an assumed live result. Preserve/expose the header through proxy/CORS configuration as applicable.
